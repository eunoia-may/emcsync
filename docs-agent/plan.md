# 规划
提示词保持极简，做好约束与引导即可，不必太详细和死板。细节方面，搜索并选择当下最流行且确实好用的做法，并告诉我、供我审阅，通过后用极简的语言固化为新的执行流 markdown，并在开头附上“此执行流基于当时的最主流、好用的做法，日后未必适用，本文件仅作为当时的施工辅助和状态快照。”

此外，若有需求，可新建“工程-<name>.md”，按施工顺序拆分为多个工程文件，每个记录每个阶段的施工计划，工程文件应使用极简但约束和引导清晰的话写下施工计划。

使用 jj 进行版本控制，完成一个阶段或者遇到需要马上保存快照以便进行测试的时候就提交一次，提交前先通知我，给出要提交的信息我看看能否提交了。

可在此文件里建立简短的施工表，对应不同的工程文件，记录哪些是完成的，哪些没完成，以便后续使用在新的对话里能快速延续先前施工。

**不入库**：牢记使用 `.gitignore` 过滤不应入库的敏感文件和噪声文件，使用中文注释说明过滤资源被过滤的原因。

**不过度**：不要过度思考（不要做无意义的思考），每次行动前，先想好行动路径，不要浪费 token

## 风格
代码清晰模块化，提交与注释使用朴素的风格，例如，当需要**使用注释来区分代码结构**时，注释不要使用这样的华丽分隔符：

```rust
// ----------
// 注释
// ----------
```

应这样，使用换行来实现视觉上的结构区分就行：

```rust
代码

// 注释

代码
```

提交不必使用花哨的 emoji，要使用清晰的语言，让人能快速明白此提交作用。

## 提醒
每当有选项式提问、提交前、完成一个阶段后、单对话结束时，使用 mako 通知我。
