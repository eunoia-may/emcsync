# 打包与推送

基于 2026-10-23 当时的做法，日后未必适用，仅作施工辅助与状态快照。

分三段：先让 Nix 用户能装，再让普通用户能下载，最后接缓存。

## 打包

### 给 Nix 用户

安装模式定为三步：用户在自己的 `flake.nix` 里加项目链接，在模块列表里引一个模块，然后在自己的包列表里写包名。项目侧负责把包挂进 `pkgs`，装不装由用户决定，不替用户做决定。

项目需要三个输出：

```nix
# 只把包挂进 pkgs，不往 systemPackages 或 home.packages 里塞东西
overlays.default = final: prev: {
  emcsync-cli = self.packages.${prev.stdenv.hostPlatform.system}.default;
};

# NixOS 用户：nixosConfiguration 的 modules 列表里引用
nixosModules.default = { lib, ... }: {
  nixpkgs.overlays = lib.mkAfter [ self.overlays.default ];
};

# home-manager 用户：用户的 imports 列表里引用
homeModules.default = { lib, ... }: {
  nixpkgs.overlays = lib.mkAfter [ self.overlays.default ];
};
```

`mkAfter` 保证用户自己的 overlay 排在本项目之后，不受引用位置影响。

用户侧长这样：

```nix
# flake.nix，inputs
emcsync-cli.url = "github:eunoia-may/emcsync-cli";

# flake.nix，系统模块列表
inputs.emcsync-cli.nixosModules.default

# system.nix
environment.systemPackages = with pkgs; [ emcsync-cli ];
```

home-manager 走同一条路，只换模块和安装位置：

```nix
# flake.nix，home-manager 的 imports
inputs.emcsync-cli.homeModules.default

# home.nix
home.packages = with pkgs; [ emcsync-cli ];
```

两条硬约束：

- overlay 必须转发到 `self.packages.${system}.default`，不能用 `callPackage` 重建。前者用 flake.lock 钉住的 nixpkgs，缓存能命中；后者用用户自己的 nixpkgs，缓存永远不命中。
- 模块里只写 `nixpkgs.overlays`，不加 `enable` 选项，也不默认安装。多一层开关只是噪音。

`packages.default` 从 `flake.nix` 抽到独立的 `package.nix`，供 `packages` 与 `overlays` 共用。抽的时候注意相对路径要跟着改。

不想用 overlay 的用户也可以直接写 `inputs.emcsync-cli.packages.${pkgs.stdenv.hostPlatform.system}.default`，等同于装了个固定份的包，不推荐但不拦。

### 给 Windows 用户

产物为 `emcsync-cli-<版本>-x86_64-pc-windows-msvc.zip`，内含 `emcsync-cli.exe`，解压到任意目录即是安装。

不自带卸载器，删除目录即可；配置文件、缓存都写在用户的游戏实例目录里，不留全局痕迹。

### 给 Linux 用户

产物为 `emcsync-cli-<版本>-x86_64-unknown-linux-musl.tar.gz`，内含二进制与 README。解压后 `chmod +x`，放进 `PATH` 即可。

用 musl 静态链接而不是 gnu，是为了不给老发行版的 glibc 版本添麻烦。代价只是构建时多一个 target。

不打 AppImage：本项目是 CLI，AppImage 的收益（双击运行、桌面集成）用不上，却要额外背一层 FUSE 依赖和打包脚本。

### 给 macOS 用户

产物为 `emcsync-cli-<版本>-<triple>.tar.gz`，`x86_64-apple-darwin` 与 `aarch64-apple-darwin` 各一份，解压即用。

未签名，首次运行会被 Gatekeeper 拦一次，需在系统设置里放行，README 里写清楚。

### 首版矩阵

六个 target：`x86_64-unknown-linux-musl`、`aarch64-unknown-linux-musl`、`x86_64-pc-windows-msvc`、`aarch64-pc-windows-msvc`、`x86_64-apple-darwin`、`aarch64-apple-darwin`。

每个平台用对应架构的原生 runner 编译，不搞交叉编译，省掉工具链配置。

## 推送

推送到 GitHub，打 `v*` 标签触发发布。工作流做三件事：按矩阵编译、打成上面那些压缩包、上传到该标签的 Release。

产物统一由 `cargo build --release` 出，不用 `nix build` 出——Nix 在 Windows 上跑不了，别为了统一而统一。

推送前先在本地 `cargo build --release` 走一遍，确认干净。

落地（2026-10-23）：仓库是 `eunoia-may/emcsync-cli`，许可证取 MIT（只放一份 `LICENSE`）。六个 target 各用同架构的原生 runner：`ubuntu-24.04`、`ubuntu-24.04-arm`、`windows-2025`、`windows-11-arm`、`macos-15-intel`、`macos-15`；其中 `windows-11-arm` 要求仓库公开，不可用时删掉该项即可。

矩阵 job 只负责编译并把自己的压缩包传成 artifact，最后由单独的 `release` job 收齐再一次建 Release（`softprops/action-gh-release`），避免六个 job 并发写同一个 Release 打架。标签版本与 `Cargo.toml` 版本不一致时直接失败。

musl 用 `musl-tools` 的 `musl-gcc` 同时当链接器与 C 编译器（`aws-lc-sys` 要编 C），其余平台不额外装东西。

首次推送注意：远端是 GitHub 建仓时自带的 `Initial commit`（只有一份 LICENSE），与本地历史没有共同祖先；本地已在 `添加 MIT 协议` 提交里放了同样的 `LICENSE`，所以用 `git push --force origin HEAD:main` 覆盖即可，不必为了合流去 rebase 出一条重复的许可证提交。

推送后本地打标签：`git tag -a v0.1.0 -m "0.1.0"`，再 `git push origin v0.1.0`。标签触发的第一次 CI 就是六平台矩阵的验证；`windows-11-arm` 若报不可用，删掉矩阵该项。

## 缓存

缓存单独一条线，不阻塞发布：CI 里对 `packages.default` 跑一次 `nix build`，用 `cachix-action` 推到 Cachix。

用户侧加两行，用 `extra-` 前缀以免覆盖默认缓存：

```nix
nix.settings = {
  extra-substituters = [ "https://<缓存名>.cachix.org" ];
  extra-trusted-public-keys = [ "<缓存名>.cachix.org-1:<公钥>" ];
};
```

缓存的生命线是上一条约束：overlay 转发 `self.packages`。改成 `callPackage` 或让用户 follows nixpkgs，存进去的 path 就对不上，白推。

缓存接入后，用户侧安装方式一个字都不用改。
